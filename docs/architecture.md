# Architecture

Express 5 registers the API in `src/app.js`. Module routers validate requests with Joi and pass validated input to services. Services coordinate transactions, pricing, state transitions and auditing; repositories and shared query helpers use parameterized `pg` queries. The facility module groups sports, resources and customers. The existing `src/services/booking.services.js` remains a compatibility export for the new booking engine.

The `facility` PostgreSQL schema isolates the new API from existing public OTP/admin tables. The old administrative API remains available under `/api/v1/legacy/auth` with its original Basic Auth and opaque session semantics; new staff use `/api/v1/auth` and `facility.users`. Existing users are not automatically promoted or migrated. Legacy setup is optional (`npm run db:setup`).

## Booking consistency

Every booking writer acquires the resource row lock before checking active reservations. Rescheduling locks both resource IDs in ascending order, then locks the booking, and rejects an intervening resource change with HTTP 409. Exclusive reservations also have a PostgreSQL GiST exclusion constraint over half-open timestamp ranges. A trigger derives the exclusive flag from the locked resource, preventing a caller from bypassing the constraint by supplying false. Shared bookings use an occupancy sweep: starts add participants, ends subtract participants, and simultaneous ends are processed first. Maximum occupancy over the requested interval determines capacity. Direct SQL writes to shared reservations must obey the same locking and capacity algorithm; application database credentials should not be exposed to other writers.

Expired holds are changed to EXPIRED before new reservations check the exclusion constraint. A background job repeats this every 30 seconds. Availability reads exclude expired holds even before cleanup. The job and payment handlers use the same lock order. Availability is a snapshot; only transactional booking creation reserves capacity.

Resource capacity/type changes and operating-hours changes are rejected while future active reservations exist. Maintenance creation rejects active overlaps. Inactive resources preserve history. Operating hours are same-day only; overnight hours must be modeled as separate future enhancements. Missing operating hours mean closed. Cancellation preserves financial records and requires a reason. Editing supports notes; time/resource changes use the reschedule endpoint. Rescheduling is rejected while an online order remains pending. It reprices with the current resource rate and rejects a price below net payments until excess is refunded. Historical prices otherwise remain unchanged.

## Financial consistency

Decimal.js computes duration-based prices and rounds once to two decimals. RESOURCE pricing ignores participant count, PARTICIPANT pricing multiplies by count. PostgreSQL NUMERIC stores all money. A booking lock serializes payment/refund updates; verified successful credits minus REFUNDED debit records determine net collections. Refund rows reference the original successful payment, with one full refund per payment. Partial payments are supported; partial refunds are not supported in this version.

Booking status is independent of financial status. Desk bookings confirm immediately. Online bookings hold inventory until a verified captured event confirms them. Late captures for cancelled/expired bookings are recorded as real financial credits, produce `LATE_PAYMENT_REQUIRES_REFUND`, and never resurrect inventory. Operators must refund them through the provider dashboard. Dashboard queries exclude cancelled/expired bookings. Full provider refunds reconcile through verified `refund.processed` events. The payment category PAID/PARTIAL/UNPAID is derived, never trusted from input.

Provider order creation happens while booking/resource locks are held to serialize initiation, with a 10-second request timeout. A provider request succeeding followed by a database/network failure can leave an orphan provider order; its ID must be reconciled operationally. No distributed transaction exists between PostgreSQL and Razorpay. Unknown orders or mismatched amounts return errors for investigation rather than attributing money to an unrelated booking. This integration supports INR and full refunds only. Real Razorpay end-to-end validation needs merchant credentials.

## Retry and security model

Booking, desk payment, online initiation and refund endpoints accept `Idempotency-Key` (up to 128 characters). Scope includes actor and operation. An advisory transaction lock serializes identical keys, the canonical validated payload hash rejects changed input, and the committed JSON response is replayed. Keys are retained indefinitely; archive only after the business retry window. Webhooks use signed raw bytes and provider event IDs plus state/unique constraints for duplicate events with different delivery IDs. The webhook must bypass JSON parsing until signature verification.

JWTs use HS256, issuer/audience checks, an eight-hour expiry, random JTI and a configurable secret. Authentication reads current user status/role on every request. Logout records the JTI until expiry (revoked tokens may be purged after expiry). ADMIN manages users and facility configuration; STAFF manages customers/bookings/payments. These are staff APIs; ONLINE booking source is not a public-customer authentication mechanism. Health and signed webhooks are unauthenticated. Login and global rate limits use per-process memory; multi-instance deployments need a shared limiter store and correctly configured trusted proxies before serving proxy traffic.

Logs contain request IDs, method, path, status and duration, not headers, request bodies, tokens or customer search query values. Error responses hide SQL/stack details. Production requires Razorpay, configured credentials and a strong JWT secret. TLS and database backups must be provided by deployment infrastructure. Startup checks migrations and connectivity; SIGINT/SIGTERM stop the HTTP server, expiration timer and pool.
